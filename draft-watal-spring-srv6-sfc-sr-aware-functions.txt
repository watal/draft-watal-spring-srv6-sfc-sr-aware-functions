             SRv6 SFC Architecture with SR-aware Functions
         draft-watal-spring-srv6-sfc-sr-aware-functions-latest

Abstract

   This document describes the architecture of Segment Routing over IPv6
   (SRv6) Service Function Chaining (SFC) with SR-aware functions.  This
   architecture provides the following benefits:

   *  Comprehensive Management: centralized control and management of SR
      Policies, network topology, service functions, and network
      metrics.

   *  Simplicity: no SFC proxies, which reduces the number of nodes and
      address resource consumption.

1.  Introduction

   Segment Routing over IPv6 (SRv6) [RFC8986] enables packet steering
   through an ordered list of instructions called a segment list.  SRv6
   supports various types of segments, including Prefix Segments,
   Adjacency Segments, VPNs, and Binding Segments.

   Service Function Chaining (SFC) [RFC7665] can be used in various
   scenarios (e.g., FW, IPS, IDS, NAT, and DPI).  SFC based on Segment
   Routing (SR) is described in
   [I-D.draft-ietf-spring-srv6-service-programming].  It defines SRv6
   Endpoint Behaviors, such as End.AS, End.AD, and End.AM, that enable
   the use of SR-unaware functions.

   This document describes an architecture for SRv6 SFC with SR-aware
   functions, which provides comprehensive management of SRv6 network
   resources and services.

   *  SFC, SFC Proxy, and Service Classification Function defined in

   *  Service Segment, SR-Aware Service, SR-Unaware Service, End.AS,

   *  Headend, Color, and Endpoint defined in [RFC9256].

   *  Quality of Service (QoS), Service Level Agreement (SLA), and

      Traffic Engineering Database (TED) defined in [RFC5440].

   *  BGP Flow Specification defined in [RFC8955] and [RFC8956].

2.2.  Newly Defined Terminology

   The following terms are used in this document as defined below:

   *  Service Function Node: an SRv6 Segment Endpoint Node that hosts
      SR-aware functions associated with service segments.

   *  SRv6 Controller: a controller consisting of a PCE and a
      Classification Rule Controller.

   *  Classification Rule Controller: a controller that distributes flow
      classification rules to SR source nodes.

   *  Service Function Manager: a manager that configures network
      function instances and enables SR-aware functions as service
      segments.

3.  Design Objectives and Assumptions

3.1.  Goals/Objectives

   The SRv6 SFC architecture is designed with two main objectives:

   *  Comprehensive Management: centralized coordination of SR Policies,
      network topology, service functions, and network metrics.

      Operators need to satisfy customer service requirements, including
      SFC requirements (e.g., required service functions and their
      order) and QoS objectives (e.g., availability, latency, and
      bandwidth).  These requirements collectively define the service
      intent.  Realizing this service intent requires coordinated
      service segment provisioning, network state collection, and SR
      Policy computation.

      [RFC8402] describes a hybrid control plane that combines
      distributed and centralized control.  In this model, forwarding
      information, such as Node and Adjacency SIDs, is distributed among
      SR nodes through IGPs such as IS-IS and OSPF, while SR Policies
      and flow classification rules are managed by centralized
      controllers.  Service segment information is configured by the
      management plane and can be advertised by service function nodes
      using BGP-LS.

      The SDN framework [RFC7426] enables network abstraction and
      automation.  An SRv6 controller can translate service intents into
      SR Policies and flow classification rules, coordinate service
      segment provisioning, monitor network and service function states,
      and apply protection mechanisms to meet service requirements.

   *  Simplicity: SR-aware functions do not require dedicated SFC
      proxies, reducing the number of nodes and address resource
      consumption.  Network complexity increases operational costs,
      particularly when multiple protocols and additional network
      components are required.  Using an SFC proxy may also increase
      forwarding overhead due to additional header manipulations.

3.2.  Assumptions

   To achieve these objectives, this architecture is based on two main
   assumptions:

   *  Straightforward extension of the SRv6 network programming model

      The protocol used in this architecture is compatible with SRv6.
      This streamlines the operation of services like traffic steering,
      including SFC, redundancy, and local protection.  Standardized
      protocols and mechanisms, such as BGP, PCEP, IS-IS, OSPF, TI-LFA,
      and Anycast SIDs, are used in this architecture.

      This architecture is compliant with the SRv6 network programming
      model and can also support SR-unaware functions using appropriate
      SRv6 endpoint behaviors.  However, it is primarily designed for
      SR-aware functions.

   *  SDN framework compliance and comprehensive management of SRv6 SFC
      by controllers

      The architecture uses standardized protocols and abstract service
      interfaces to support automated and intent-based management of
      SRv6 SFC.  This also provides programmability by controlling
      policies that meet a user's intent, including SFC and QoS.

4.  Overview of Architecture

   Figure 1 illustrates an overview of this architecture.

    +----------------------- Application Plane ----------------------+
    |                        User Application                        |
    +-----------------------------------|----------------------------+
                                        |
    +- Control Plane (SRv6 Controller) -v-----+ +- Management Plane -+
    | +--------------+ +--------------------+ | | +----------------+ |
    | |Classification| |        Path        | | | |    Service     | |
    | |     Rule     | |     Computation    | | | |    Function    | |
    | |  Controller  | |    Element (PCE)   | | | |    Manager     | |
    | +------|-------+ +-^-------|--------^-+ | | +----------------+ |
    +--------|-----------|-------|--------|---+ +---------|----------+
             |           |       |        |               |
    +--------|-----------|-------|--------|---------------|---+
    | +------v-----------|-------v-+    +-|---------------v-+ |
    | |                            |    |      Service      | |
    | |       SR Source Node       |----|      Function     | |
    | |                            |    |        Node       | |
    | +----------------------------+    +-------------------+ |
    +------------------- Forwarding Plane --------------------+

    Figure 1: Overview of SRv6 SFC Architecture with SR-aware Functions

   This architecture is based on [RFC7426] and consists of the
   forwarding plane, control plane, management plane, and application
   plane.

   *  Forwarding Plane: classifies packets, encapsulates them with an
      IPv6 header and Segment Routing Header (SRH), and forwards them
      through SRv6 Endpoint Behaviors.

      -  Provides SR-aware functions using End.AN.

      -  Classifies and steers traffic flows into corresponding SR
         Policies using policy-based routing (PBR).

      -  Provides redundancy using Anycast SIDs and local protection
         using Fast Reroute (FRR).

   *  Control Plane: makes decisions about packet forwarding and
      provides rules for a forwarding plane.

      -  Collects link-state, including SRv6 locators, prefixes,
         behaviors, and delays.

      -  Calculates and provisions SR Policies.

      -  Applies SR Policies to each flow by provisioning flow
         classification rules.

   *  Management Plane: deploys and monitors network functions and
      devices.

      -  Sets up network functions.

      -  Collects metrics of devices, network functions, and SFC
         services.

   *  Application Plane: provides a user API for the control and
      management planes.

      -  Offers an interface for operators or customers.

      -  Applies intents defined in [RFC9315].

   The components are loosely coupled and communicate using standardized
   protocols and abstraction layers.

   The detailed design of the application plane is outside the scope of
   this document, as its components and abstraction layers depend on
   network requirements and operator intent.  The following sections
   describe the forwarding plane, control plane, and management plane in
   detail.

5.  Forwarding Plane

   The forwarding plane realizes SFC through packet classification, SRv6
   encapsulation, and service function processing within the SR domain.
   In this architecture, all forwarding plane components are located
   within the SR domain.

    +-----------------------------------------------------------------+
    | +-----------+             +----------+             +----------+ |
    | |           | SRv6 Packet | Service  | SRv6 Packet | Service  | |
    | | SR Source |(S2,S1; SL:1)| Function |(S2,S1; SL:1)| Function | |
   -->|    Node   |------------>|   Node   |------------>|   Node   |-->
    | |           |             |   (S1)   |             |   (S2)   | |
    | +-----------+             +----------+             +----------+ |
    +--------------------------- SR domain ---------------------------+

                         Figure 2: Forwarding Plane

   Figure 2 shows an example of SFC with two network functions.  First,
   the SR source node classifies the flow and encapsulates it with an
   SRH containing the segment list <S1, S2>.  Next, the service function
   node (S1) receives the packet and applies the network function
   associated with the End.AN SID S1.  Finally, the service function
   node (S2) receives the packet and applies the network function
   associated with the End.AN SID S2, thus completing the SFC.

5.1.  End.AN-based Service Segment Provisioning

   End.AN is an SRv6 Endpoint Behavior for SR-aware service functions.
   It MAY support optional arguments to provide additional
   programmability for network functions.

   By using virtualized spaces within routers or on generic servers,
   network functions can be provided at any node in an SR domain.  This
   allows for scaling and flexible redundancy of network functions.

5.1.1.  When a Network Function Becomes Unavailable

   When a network function becomes unavailable, the affected node MUST
   stop processing packets using the corresponding SID.

   For an Anycast SID, the affected node SHOULD withdraw its SID
   advertisement, allowing routing convergence to direct traffic to
   another available service function node.

   If no other service function nodes are available, packets MUST be
   dropped.  The node MAY send an ICMPv6 message (Type 1: Destination
   Unreachable, Code 0: no route to destination).

5.1.2.  Anycast Segment

   The concept of the Anycast Segment is introduced in [RFC8402].  An
   Anycast SID allows multiple service function nodes providing the same
   network function to share a common SID, enabling redundancy and
   traffic distribution.

   An Anycast SID does not guarantee session continuity or state
   consistency across service function nodes.

   For stateful Service Functions, the deployment MUST provide
   mechanisms to maintain session affinity and ensure service state
   consistency across instances.  When traffic is forwarded to another
   instance, the deployment MUST ensure that the required service state
   is available before packet processing.

   The specific mechanisms for session affinity, state synchronization,
   and failover are outside the scope of this document.

5.1.3.  Fast Reroute

   The segment list defines the ordering of network functions in an SRv6
   SFC.  FRR MUST preserve the order of service functions specified by
   the SR Policy when providing local protection for the path to an
   active segment.

   If the Active Segment is an Anycast SID, the packet MAY be forwarded
   to another service function node.

   The failure recovery mechanisms described in this section are
   intended to maintain network connectivity and service function node
   reachability.  For stateful service functions, the requirements
   described in the Anycast Segment section also apply when FRR forwards
   packets to another service function node.

5.2.  Service Function Chains

   In this architecture, each SFC is represented by an SR Policy, whose
   Color indicates its purpose or intent.

   An SFC can be realized using either strict or loose source routing.
   When QoS requirements are also considered, the PCE computes paths
   that satisfy the specified constraints.  Flex-Algo SIDs MAY be used
   to steer traffic over paths that meet specific constraints.

5.3.  Per-Flow Classification and Steering

   In an SR source node, which serves as the Service Classification
   Function, packets are classified on a per-flow basis using PBR and
   steered into the corresponding SR Policy.  The SR source node MUST
   support packet classification based on the criteria specified in the
   flow classification rules, which may include a 5-tuple or more
   detailed packet information.

   To support comprehensive management, the Service Classification
   Function has an API to communicate with the controller.

6.  Control Plane

   The control plane sets up a forwarding plane by creating SR Policies
   for SFC and provisioning flow classification rules to associate them
   with traffic flows.

    +- Control Plane (SRv6 Controller) -------+
    | +--------------+ +--------------------+ |
    | |Classification| |        Path        | |
    | |     Rule     <->     Computation    | |
    | |  Controller  | |    Element (PCE)   | |
    | +------|-------+ +-^-------|--------^-+ |
    +--------|-----------|-------|--------|---+
     Classification link-state SR Policy Service Segment
           Rule      (BGP-LS)  (PCEP)    (BGP-LS)
     (BGP FlowSpec)      |       |        |
    +--------|-----------|-------|--------|-------------------+
    | +------v-----------|-------v-+    +-|-----------------+ |
    | |                            |    |      Service      | |
    | |       SR Source Node       |----|      Function     | |
    | |                            |    |        Node       | |
    | +----------------------------+    +-------------------+ |
    +------------------- Forwarding Plane --------------------+

                          Figure 3: Control Plane

   The SRv6 Controller consists of the following two components:

   *  PCE: computes SR Policies that fulfill SFC and QoS requirements
      from the headend to the endpoint, and provisions them to the SR
      source node.

   *  Classification Rule Controller: distributes flow classification
      rules that associate traffic flows with SR Policies to SR source
      nodes.

6.1.  Path Computation Element (PCE)

   A PCE computes and provisions SR Policies.  As an active stateful PCE
   [RFC8231], it establishes PCEP sessions with PCCs in an SR domain and
   manages SFC-related SR Policies under its stateful control.  The PCE
   MUST support the computation and provisioning of SR Policies with
   both explicit and dynamic paths.

   For dynamic path computation, the PCE uses the Constrained Shortest
   Path First (CSPF) algorithm to compute paths that satisfy both
   service function requirements and QoS constraints.

   The PCE builds a Traffic Engineering Database (TED) of the SR domain
   using BGP-LS and installs SR Policies via PCEP [RFC9603] [RFC9862].

   The BGP-LS Service Segment extension
   [I-D.draft-ietf-idr-bgp-ls-sr-service-segments] can be used to
   advertise service segment information.  The PCE uses this
   information, together with network topology and traffic engineering
   metrics, to compute SR Policies that include the required service
   functions.

6.2.  Classification Rule Controller

   A Classification Rule Controller determines which SFC to apply to
   each traffic flow.

   The resulting classification rules are distributed to each SR source
   node using the BGP Flow Specification extension defined in
   [I-D.draft-ietf-idr-ts-flowspec-srv6-policy].  The rules associate
   traffic flows with SR Policies identified by their Color and
   Endpoint.

   The SRv6 Controller is responsible for maintaining the association
   between traffic classification rules and SR Policies.  For a given
   headend, the combination of Color and Endpoint MUST uniquely identify
   an SR Policy within the SRv6 Controller.  A Color value MAY be reused
   with different Endpoints or in multiple FlowSpec rules that reference
   the same SR Policy.

   The PCE computes and provisions SR Policies, whereas the
   Classification Rule Controller distributes the corresponding FlowSpec
   rules to SR source nodes.  This separation allows traffic
   classification and path computation to be managed independently
   within the SRv6 Controller.

6.3.  Handling SR Policy Unavailability

   The Stateful PCE monitors the state of SR Policies under its stateful
   control through PCEP state reporting.  When an SR Policy becomes
   unavailable or is removed from a PCC, the Stateful PCE detects the
   change and may take appropriate actions, such as recomputing and
   reprovisioning the SR Policy.

   FlowSpec rules may be distributed independently of the operational
   state of their associated SR Policies.  A PCC may receive a FlowSpec
   route before the corresponding SR Policy becomes available.  In such
   a case, the PCC does not activate the associated traffic-steering
   state until the SR Policy becomes available.  The PCC MAY log this
   condition for operational visibility.  This behavior does not require
   extensions to the BGP Flow Specification encoding or distribution
   procedures.

   The PCE and the Classification Rule Controller coordinate as
   necessary to maintain the association between traffic flows and SR
   Policies.  If the existing FlowSpec rule remains applicable to the
   reprovisioned SR Policy, no change to the rule is necessary.
   Otherwise, the Classification Rule Controller withdraws the obsolete
   rule before distributing an updated rule.

   Once the SR Policy and the corresponding FlowSpec rule are both
   available at the PCC, the PCC associates the traffic flows with the
   SR Policy using the Color and Endpoint specified in the FlowSpec
   rule.

7.  Management Plane

   The management plane configures network function instances, enables
   SR-aware functions as service segments, monitors resources, and
   collects network metrics.  The details of each manager are outside
   the scope of this document, as the southbound interface of the
   management plane may be different for each service and hardware
   architecture.

    | +-----------+ +--------------+ +-----------+ +-----------+ |
    | |  Service  | | Virtualized  | |    VNF    | |  Network  | |
    | |  Function | |Infrastructure| |  Manager  | |  Metric   | |
    | |  Manager  | |   Manager    | |           | |  Manager  | |
    | +-----|-----+ +------^-------+ +-----|-----+ +-----^-----+ |
    +-------|--------------|---------------|-------------|-------+
            |              |               |             |
                Management Plane Southbound Interfaces
            |              |               |             |
    +-------|--------------|---------------|-------------|--------+
    | +-----v--------------v---------------v-------------|------+ |
    | |                  Service Function Node                  | |
    | +---------------------------------------------------------+ |
    +------------------------- SR domain -------------------------+

                         Figure 4: Management Plane

   Figure 4 shows examples of managers that MAY be added to a management
   plane:

   *  Service Function Manager: assigns SIDs to network functions and
      manages their service segment configuration.

   *  Virtualized Network Function Manager (VNFM): manages the lifecycle
      of network functions.

      -  It instantiates, configures, scales, heals, updates, and
         terminates network functions.

   *  Virtualized Infrastructure Manager (VIM): manages virtualized
      compute, storage, and network resources.

      -  In SRv6 SFC, a VIM MAY manage virtualized environments hosted
         on generic servers or within routers.

   *  Network Metrics Manager: collects metrics for SR Policy
      calculation and evaluation.

      -  Metrics are collected from multiple data sources, including
         IPFIX, TCP statistics, and SRv6 path tracing
         [I-D.draft-filsfils-ippm-path-tracing].

      -  Metrics can be used as input for PCE path computation.

7.1.  Service Function Manager

   The Service Function Manager configures service function nodes to
   enable or disable their service segments using the following
   parameters:

   *  Behavior: End.AN

   *  SID: The End.AN SID in IPv6 address format.

   *  Function Name: The type of network function.

   *  Action: Enable or disable.

   *  Management Parameters (OPTIONAL):

      -  Function-specific parameters: Parameters and context associated
         with a particular network function.

      -  Anycast Group: Identifies the group of service function nodes
         sharing an Anycast SID.  This parameter MUST be configured when
         multiple nodes provide the same service function using an
         Anycast SID.

7.2.  Security Considerations

   This document describes an SRv6 SFC architecture using SR-aware
   functions.  The security considerations for SRv6 and its associated
   control-plane protocols also apply to this architecture.

   Service Function Nodes MUST validate and filter incoming SRv6 packets
   to prevent unauthorized access to service functions.

   Service function information advertised through BGP-LS SHOULD be
   protected against unauthorized modification or injection, as
   incorrect information may cause the PCE to compute inappropriate SR
   Policies.

   PCEP sessions between the PCE and PCCs SHOULD be protected against
   unauthorized access and modification.

   Flow classification rules distributed by the Classification Rule
   Controller SHOULD be protected against unauthorized modification or
   injection to prevent unintended traffic steering.

   Management interfaces used to configure service function instances
   SHOULD be protected against unauthorized access and modification.

   For service functions using Anycast SIDs, operators SHOULD consider
   the security implications of forwarding traffic to different service
   function instances and synchronizing service state across instances.
   State synchronization mechanisms SHOULD be protected against
   unauthorized access and modification.

   The security mechanisms for the underlying protocols and management
   interfaces are outside the scope of this document.  Implementations
   and deployments SHOULD follow the relevant security recommendations
   in the corresponding specifications.

Appendix A.  Implementation Experience

   Note to the RFC Editor: Please remove this appendix before
   publication as an RFC.

   This appendix is informative and non-normative.

   Several components of the architecture have been implemented and
   validated in IETF Hackathons.

   A.1.  Flow-based Service Classification

   The following functionality has been implemented in GoBGP:

   *  Advertisement of classification rules using BGP FlowSpec
      extensions for SRv6 Policy.

   A.2.  SR Policy Computation and Provisioning

   The following functionality has been implemented in Pola PCE:

   *  Centralized SR Policy computation for SFC using a stateful PCE.

   *  Support for explicit and dynamic SRv6 Policies with loose source
      routing.

   A.3.  Service Segment Advertisement

   The following functionality has been implemented in GoBGP and ExaBGP:

   *  Advertisement of VNF and End.AN information using BGP-LS Service
      Segment extensions.

   A.4.  Service and Infrastructure Management

   The following functionality has been implemented using OpenStack and
   Ansible:

   *  Deployment of VNFs.

   *  Provisioning of SRv6 End.AN behaviors.
